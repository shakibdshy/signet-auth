The `@shakibdshy/signet-client` package is generated from Signet's OpenAPI contract, so the
methods and error codes match the server. You need **Node.js 20+**.

## Install

The package is not published to npm yet. Until it is, install it from a local checkout of this
repository:

```bash
cd /path/to/signet/client/ts
npm install
npm run build

cd /path/to/your-frontend
npm install /path/to/signet/client/ts
```

When a published version is available, this becomes `npm install @shakibdshy/signet-client`.

## Create the client

```ts
import { createSignetClient, SignetApiError } from '@shakibdshy/signet-client';

export const auth = createSignetClient({
  // Origin + your backend's Config.PathPrefix. If the Go server mounts
  // auth.Handler() at /auth, baseURL MUST include /auth.
  baseURL: 'https://api.example.com/auth',
});
```

<Callout title="Most common mistake">
Using only `https://api.example.com` as `baseURL` when the backend mounts Signet at `/auth`.
The generated client calls `/signup`, so without the prefix every request goes to
`https://api.example.com/signup` and returns 404.
</Callout>

Cookies are included automatically. The client fetches a CSRF token from `GET /csrf-token`,
caches it, and sends `X-CSRF-Token` on state-changing calls. You do not manage CSRF yourself.

## A complete login form

```tsx
import { useState } from 'react';
import { auth, SignetApiError } from './signet-client';

export function Login() {
  const [email, setEmail] = useState('');
  const [password, setPassword] = useState('');
  const [error, setError] = useState('');
  const [user, setUser] = useState<{ email: string } | null>(null);
  const [challenge, setChallenge] = useState('');
  const [code, setCode] = useState('');

  async function submit(event: React.FormEvent) {
    event.preventDefault();
    setError('');
    try {
      const result = await auth.signIn({ email, password });
      if (result.two_factor_challenge) {
        setChallenge(result.two_factor_challenge);
        return;
      }
      setUser(result.user);
    } catch (err) {
      setError(err instanceof SignetApiError ? 'Invalid email or password.' : 'Something went wrong.');
    }
  }

  async function verifySecondFactor(event: React.FormEvent) {
    event.preventDefault();
    setError('');
    try {
      const result = await auth.verifyTwoFactor({ challenge, code });
      setUser(result.user);
    } catch (err) {
      setError(err instanceof SignetApiError ? 'Invalid or expired code.' : 'Something went wrong.');
    }
  }

  async function logout() {
    await auth.signOut({});
    setUser(null);
  }

  if (user) {
    return <div>Signed in as {user.email} <button onClick={logout}>Sign out</button></div>;
  }
  if (challenge) {
    return (
      <form onSubmit={verifySecondFactor}>
        <input value={code} onChange={e => setCode(e.target.value)} placeholder="Authenticator code" />
        <button type="submit">Verify</button>
        {error && <p role="alert">{error}</p>}
      </form>
    );
  }
  return (
    <form onSubmit={submit}>
      <input value={email} onChange={e => setEmail(e.target.value)} placeholder="Email" />
      <input type="password" value={password} onChange={e => setPassword(e.target.value)} />
      <button type="submit">Sign in</button>
      {error && <p role="alert">{error}</p>}
    </form>
  );
}
```

`signUp` works the same way. To render the signed-in User on page load, call the `/session`
endpoint or expose the User from your own server-rendered route; the client does not keep a
reactive session store.

## Passwordless sign-in

These endpoints are anonymous and CSRF-exempt.

```ts
await auth.sendMagicLink({
  email: 'ada@example.com',
  callback_url: 'https://app.example.com/welcome', // must be allowlisted on the server
});

// If your app owns the link route, exchange the token from the URL:
const sent = await auth.verifyMagicLink({
  token: new URL(location.href).searchParams.get('token')!,
  callback_url: 'https://app.example.com/welcome',
});

await auth.sendOtp({ email: 'grace@example.com' });
const result = await auth.verifyOtp({ email: 'grace@example.com', code: '123456' });
```

A normal clicked link navigates to `GET /verify-magic-link`, which sets cookies and redirects;
call `verifyMagicLink()` only when your frontend handles that route itself.

## Last sign-in method

When the backend enables [Last sign-in method](/docs/defensive-controls), the client can read the
signed cookie through the typed endpoint. Create the client with the backend `PathPrefix` included
in `baseURL`:

```ts
import { createSignetClient } from '@shakibdshy/signet-client';

const auth = createSignetClient({ baseURL: 'https://api.example.com/auth' });
const { method } = await auth.lastSignInMethod();
// "password" | "username" | "magic-link" | "email-otp" | a provider name | ""
```

<Callout title="Common mistake">
Using only `https://api.example.com` as `baseURL` makes the generated client call
`/last-sign-in-method` instead of `/auth/last-sign-in-method`. The backend then returns 404.
</Callout>

The value is `""` when the feature is disabled, the cookie is absent, or its signature is invalid.
This is a read of a non-essential cookie; it does not establish a Session.

## Second factor management

```ts
const enabled = await auth.enableTwoFactor({ password });
await auth.verifyTwoFactor({ challenge: enabled.challenge, code: '123456' });
const fresh = await auth.regenerateBackupCodes({ password });
await auth.disableTwoFactor({ password });
```

Enable, regenerate and disable are authenticated. Enrollment stays pending until the first
successful TOTP code; only then will `signIn` return a challenge.

## Handling errors

```ts
try {
  await auth.verifyOtp({ email, code });
} catch (err) {
  if (err instanceof SignetApiError) {
    switch (err.code) {
      case 'invalid_code':
      case 'invalid_link':
        return showMessage('That code or link is no longer valid. Request a new one.');
      case 'code_already_used':
      case 'link_already_used':
        return showMessage('You already used that proof. Request a new one.');
      case 'two_factor_required':
        return showMessage('Enter your authenticator code to continue.');
      case 'invalid_request':
        return showMessage('That sign-in link is not valid for this app.');
      case 'rate_limited':
        return showMessage('Too many attempts. Try again shortly.');
    }
  }
  throw err;
}
```

All codes are listed in [Errors](/docs/errors); request and response shapes come from the
generated [OpenAPI contract](/docs/openapi). Server setup lives in [Passwordless sign-in](/docs/passwordless),
[Second factor](/docs/two-factor) and [Username and accounts](/docs/accounts).

## OAuth providers

Google, GitHub and [generic OIDC](/docs/oidc) providers all use the same OAuth endpoints. The
provider ID is whatever the backend registered in `Config.OAuth.Providers`.

```ts
const { url } = await auth.oauthStart({
  provider: 'acme',
  redirect: 'https://app.example.com/callback', // must be allowlisted on the backend
});

window.location.assign(url);
```

The full browser flow:

1. Your page calls `oauthStart` and redirects to the returned provider `url`.
2. The provider authenticates the User and redirects to the backend callback
   (`GET /auth/oauth/callback`). Signet owns this endpoint — do not implement it.
3. Signet redeems the code, verifies the identity and creates a Session cookie.
4. The backend redirects to your `redirect` URL. Read session state from your own app; the typed
   client does not keep a reactive session store.

If the User's email is not verified by the provider, the callback response carries a `link_token`
instead of a Session. Pass it to your backend's explicit account-linking step before treating the
User as signed in.

## Separate backend repository

The backend team can merge this base spec into its own application spec and publish a versioned
SDK. The frontend then depends on that SDK; a breaking server shape change becomes a major
version and fails the build at the affected call sites. See [HTTP API](/docs/http-api).

## API keys

API keys are for non-human clients (CI jobs, scripts, server-to-server calls). The browser never
creates or holds a raw key in a persisted store — your backend issues it with Go's
`Client.CreateAPIKey` and shows the raw value to the user **once**. The frontend can still call the
typed endpoints for management and verification:

```ts
// Issue a key — the backend's session cookie authenticates the owner.
const created = await auth.createApiKey({
  name: 'ci-pipeline',
  roles: ['ci'],
  remaining: 100,
});
showOnce(created.raw); // display once; never persist it in localStorage

// List and revoke keys owned by the signed-in User.
const { keys } = await auth.listApiKeys();
await auth.revokeApiKey({ id: keys[0].id });

// Verify a key from a non-human client (X-API-Key header, no Session).
const principal = await auth.verifyApiKey(rawKeyFromYourScript);
// principal.owner_user_id, principal.roles
```

For a browser app that authenticates **by key** on specific routes, the backend sets
`Config.APIKeyProtectedEndpoints`; on those routes the `X-API-Key` header is required and the
session cookie is ignored. There is no mixed principal. See [API keys](/docs/api-keys).

## Organizations

Create an Organization, manage Members and switch the active Organization for the authenticated
visit. The active organization lives in a signed cookie, so it survives navigation but cannot be
forged by the client.

```ts
// Create and list Organizations.
const created = await auth.createOrganization({ name: 'Acme' });
const orgId = created.Organization.id;
const { Organizations: orgs } = await auth.listOrganizations();

// Manage Memberships. Role changes are guarded by the backend Authorizer.
await auth.addOrganizationMember({ organization_id: orgId, user_id: userId, role: 'member' });
const { Members: members } = await auth.listOrganizationMembers(orgId);
await auth.setOrganizationMemberRole({ organization_id: orgId, user_id: userId, role: 'admin' });
await auth.removeOrganizationMember({ organization_id: orgId, user_id: userId });

// Select, read and clear the active Organization.
await auth.setActiveOrganization({ organization_id: orgId });
const active = await auth.activeOrganization(); // { id: '...' }
await auth.clearActiveOrganization();
```

Every mutation requires a CSRF token (the client handles it automatically) and a fresh Session on
the backend. A tampered active-organization cookie is treated as absent — always verify the value
returned by `activeOrganization()` against your own data before rendering privileged UI. See
[Organizations](/docs/organizations).

## Admin management

Admin endpoints are guarded by the backend's permission checks, fresh Session and Audit events —
the frontend only calls them. The permission model is described in [Authorization](/docs/authorization).

```ts
const { Users: users } = await auth.adminListUsers();
await auth.adminSetUserRole({ user_id: userId, roles: ['admin'] });
await auth.adminBanUser({ user_id: userId, reason: 'abuse' });
await auth.adminUnbanUser({ user_id: userId });

const { Sessions: sessions } = await auth.adminListUserSessions(userId);
await auth.adminRevokeUserSession({ session_id: sessions[0].id });
```

A `forbidden` (403) response means a missing grant, a stale Session, or a self-action block — show
a generic "not allowed" message; do not expose which check failed. See
[Admin management](/docs/admin-management) and [Errors](/docs/errors).

## Impersonation

Impersonation creates a short-lived Session for the target User and a signed one-hour cookie
holding the administrator ID and original Session token. The typed client handles both cookies:

```ts
const result = await auth.impersonate({ user_id: targetId });
// result.Token is the temporary Session; the browser now acts as the target.
// The client clears its cached CSRF token because the Session changed.

// Later — revoke the temporary Session and restore the original one.
await auth.stopImpersonating(result.Token);
await auth.clearCsrfToken();
```

While impersonating, admin checks use the administrator ID from the cookie, not the target User.
The self-service account-deletion flow is disabled during impersonation. Treat a `forbidden`
response from any guarded call as a reason to exit the impersonated view. See
[Admin management](/docs/admin-management).

## Passkeys

Passkeys are a phishing-resistant first factor. The backend configures the Relying party and stores credentials; the browser only handles the WebAuthn ceremony and the opaque ceremony token returned by Signet.

```ts
// Enroll — the caller must already have a Session.
const begin = await auth.beginPasskeyRegistration({ user_id: userId });
const credential = await navigator.credentials.create({
  publicKey: begin.options.publicKey,
});
await auth.finishPasskeyRegistration({
  token: begin.token,
  response: credential,
});

// Sign in — discoverable, so no username is needed.
const challenge = await auth.beginPasskeySignIn();
const assertion = await navigator.credentials.get({
  publicKey: challenge.options.publicKey,
  // Conditional mediation lets the browser offer the passkey as autofill.
  // Pair it with an input using autocomplete="username webauthn".
  mediation: 'conditional',
});
const result = await auth.finishPasskeySignIn({
  token: challenge.token,
  response: assertion,
});
// result.session_token is set as a cookie by the backend.

// Manage passkeys.
const { passkeys } = await auth.listPasskeys();
await auth.deletePasskey({ credential_id: passkeys[0].id });
```

Do not persist the ceremony token or the raw credential response in local storage — they are single-use. If a ceremony fails, call `beginPasskeyRegistration` or `beginPasskeySignIn` again to get a fresh challenge. The typed client clears its cached CSRF token after a passkey sign-in because the Session changes. See [Passkeys](/docs/passkeys) for the backend setup.

## Automatic sign-in

The typed client already returns the optional session token from Sign-up and email verification. When the backend enables automatic sign-in, no second `signIn` call is needed:

```ts
const signedUp = await auth.signUp({ email, password, name });
if (signedUp.session_token) {
  // A Session cookie is already set; proceed straight into the app.
}

const verified = await auth.verifyEmail({ token });
if (verified.session_token) {
  // Verification issued a Session and set the cookie.
}
```

The token is optional: it is absent whenever the matching automatic sign-in switch is off. See [Verification and reset](/docs/verification-and-reset) for the backend setup.


## Authorization server

The typed client exposes the new OAuth endpoints. Authorization code and device flows are described fully in [Authorization server](/docs/authorization-server).

```ts
// Authorization code with PKCE (the User must have a Session).
const authz = await auth.oauthAuthorize({
  client_id: 'cli',
  redirect_uri: 'http://localhost:8080/callback',
  response_type: 'code',
  scope: 'openid email',
  code_challenge: challenge,
});
const tokens = await auth.oauthToken({
  grant_type: 'authorization_code',
  code: authz.code,
  code_verifier: verifier,
  client_id: 'cli',
});

// Device flow: display the user code, then poll until approval.
const device = await auth.beginDeviceAuthorization({
  client_id: 'tv', scope: 'openid',
});
const deviceTokens = await auth.oauthToken({
  grant_type: 'urn:ietf:params:oauth:grant-type:device_code',
  code: device.device_code,
});
```


## Organization SSO

```ts
const start = await auth.startSSOSignIn({ email: 'member@acme.com' });
window.location.assign(start.url);
// On your callback page, read state and code from the URL:
const result = await auth.completeSSOSignIn(state, code);
// result.session_token and result.organization_id are set.

const connections = await auth.listSSOConnections();
await auth.createSSOConnection({
  organization_id: orgId, issuer, client_id, client_secret, domains: ['acme.com'],
});
await auth.deleteSSOConnection(connections[0].id);
```

## React session hooks

An optional `@shakibdshy/signet-react` package provides reactive session state around the generated client. Install it from a checkout alongside the typed client:

```bash
npm install /path/to/signet/client/ts
npm install /path/to/signet/client/react
```

```tsx
import { SignetProvider, useSession } from '@shakibdshy/signet-react';
import { auth } from './signet-client';

function Root() {
  return (
    <SignetProvider client={auth}>
      <Profile />
    </SignetProvider>
  );
}

function Profile() {
  const { status, user, error, signIn, signOut } = useSession();
  if (status === 'loading') return <p>Loading…</p>;
  if (status === 'anonymous') return <button onClick={() => signIn({ email, password })}>Sign in</button>;
  return <button onClick={() => signOut()}>Sign out {user?.email}</button>;
}
```

`useSession()` reads `GET /me` on mount and after sign-in, so a page reload does not need a second login. It exposes the generated client's `SignetApiError` unchanged. For server middleware, call `sessionGuard(authURL, cookieHeader)`; it checks `/me` with the incoming cookies. The hooks package is optional React glue — the Go API and HTTP contract are unchanged apart from the `/me` endpoint.
